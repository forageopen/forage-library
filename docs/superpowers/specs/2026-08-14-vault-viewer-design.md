# Vault Viewer — Design Spec

Date: 2026-08-14
Status: Approved by user, ready for implementation planning

## Summary

Replace the current hand-authored article model (`articles/`, `frameworks/`,
`courses/`, `templates/article-template.html`) with a **vault**: a folder tree
of raw source files (`.md`, `.docx`, `.pptx`, `.txt`) committed to the repo,
browsed and rendered in-browser by a generic client-side viewer — "a public
Obsidian." Authors add content by dropping a file anywhere under `vault/` and
pushing; no template to copy, no manual link to add to `index.html`.

The same viewer also supports a **private local mode**: any visitor can drag
their own file onto the viewer to read it client-side, without it touching
the repo or being visible to anyone else.

Two things are explicitly out of scope for this build (both confirmed with
the user):
- Creating/editing your own new notes from scratch — a separate future
  feature.
- PDF export for vault files, and a "download original file" action.

## Goals

- Browse a public, version-controlled folder tree of documents (the vault)
  through a sidebar, rendered with Forage Library's existing ribbon/theme.
- Render `.md`, `.docx`, `.txt`, `.pptx` content consistently, restyled into
  Forage's own typography/theme rather than preserving each format's native
  visual fidelity.
- Let a visitor drop in their own file and read it privately, using the same
  rendering engine, with nothing persisted or shared.
- Let a visitor keep private, per-file reading notes in a togglable side
  panel, persisted only in their own browser.
- Support Obsidian-style split-pane viewing of two files at once.
- No backend, no accounts, no build step for authoring — consistent with the
  existing "no closed platform" philosophy.

## Non-goals

- Full visual fidelity to the original docx/pptx (fonts, exact layout,
  positioning) — content is restyled into Forage's look.
- A note *creation* feature (blank new notes, editing tools) — only reading
  annotations on existing vault files.
- PDF export, "download original," accounts, sync, or a backend/database.
- Migrating anything beyond the single existing sample article.

## Architecture

### Rendering: client-side engine, one code path

A single JS module (`assets/js/vault-render.js` or similar) converts a file
— given either a fetched `ArrayBuffer`/text from the vault or a local `File`
object dropped by a visitor — into Forage-styled HTML in the browser. This
is deliberately one code path for both the public vault and the private
local mode, since local files can never be pre-rendered server-side anyway.

Per-type handling:
- **`.md`** → `marked` (CDN) to HTML, then Forage typography classes applied.
- **`.docx`** → `mammoth.js` browser build (CDN) converts to structured HTML
  (headings, paragraphs, lists, tables, inline images as data URIs).
  Mammoth already discards most original visual styling by design, which
  matches the "restyle" requirement directly.
- **`.txt`** → rendered as plain paragraphs (or `<pre>` if content looks
  preformatted).
- **`.pptx`** → bespoke parser: `JSZip` (CDN) unzips the file client-side,
  `DOMParser` reads each `ppt/slides/slideN.xml`, text runs are grouped by
  placeholder type (title vs. body/content) to build a title + bullet
  structure per slide, and referenced media (`ppt/media/*`, resolved via
  each slide's `_rels`) are extracted and embedded as `<img>` — placed
  inline near the text they were associated with rather than
  pixel-positioned. Each slide renders as one restyled "slide" block
  (matches the pptx mockup: centered title/subtitle style for title-only
  slides, heading + bullet list + images for content slides), with a
  slide-position rail at the bottom of the viewer.
- Rendering is async; the viewer shows a loading state while a file is being
  parsed (docx/pptx parsing is not instant).

### Vault structure & manifest

```
vault/
├── manifest.json                 ← generated by CI on every push
├── Welcome/
│   └── generative-ai-documentation-process.md   ← migrated sample article
```

Static hosting (GitHub Pages) can't list directories, so a CI step (replacing
today's `export-pdfs` job in `.github/workflows/publish.yml`) walks `vault/`
on every push and writes `vault/manifest.json`, a tree of:

```json
{ "name": "Welcome", "type": "folder", "children": [
  { "name": "generative-ai-documentation-process.md", "type": "file",
    "path": "vault/Welcome/generative-ai-documentation-process.md",
    "fileType": "md", "title": "Generative AI Documentation Process",
    "date": "2026-08-05" }
]}
```

This is committed back to the repo, same pattern as today's auto-committed
PDFs. The sidebar fetches it once on load and renders the real folder tree
(no manual index-file maintenance, unlike the current "add an `<li>` to
`index.html`" step).

**Metadata derivation** (no author-authored frontmatter required):
- Title: first `#`/H1 in `.md`; docx/pptx's own title (first heading /
  title placeholder); else prettified filename.
- Date: file's last-modified date from git history, computed at
  manifest-generation time — same idea as `ribbon.js`'s `data-published`
  formatting today.

### Page shell & UI

New page at `vault/index.html` (`/vault/` route), reusing the existing
ribbon component (title, share, copy-link, theme toggle, kebab menu) plus
three regions:

- **Left sidebar** — folder tree from `manifest.json`; click a file to open
  it in the main pane. Collapsible.
- **Main pane** — active file rendered via the engine above. md/docx/txt
  render as Forage-styled prose; pptx renders as a vertical stack of
  restyled slide blocks with a bottom slide-position rail.
- **Right "Sidenote" panel** — private per-file reading notes, persisted in
  `localStorage` keyed by the vault file's path (or a generated key for
  local-mode files). Closed by default; opened via the kebab menu
  ("Sidenote" action). Never committed, never shared — visible only in the
  visitor's own browser.

**Split view:** a kebab action ("Open in split") opens a second, independent
pane sharing the main area — two files, two independent scroll positions.
Purely Obsidian-style side-by-side reading, not a diff/compare tool.

**Private local mode:** the empty state (drop-zone: "Choose files or drop
files here") — dropping or choosing a file renders it immediately via the
same engine, sourced from `FileReader`/`File` instead of `fetch()`. Nothing
about this touches the vault, the sidebar, or the manifest.

### Migration & cleanup

- Convert the existing sample article
  (`articles/generative-ai-documentation-process.html`) to
  `vault/Welcome/generative-ai-documentation-process.md`.
- Remove `articles/`, `frameworks/`, `courses/`,
  `templates/article-template.html`, and the corresponding
  "vibe-writing loop" / repository-structure sections of `README.md`
  (replaced with vault-authoring instructions).
- Remove the PDF-export CI job and `scripts/export-pdfs.mjs` /
  `puppeteer` dependency (PDF export dropped per user decision); replace
  with the manifest-generation CI step.
- Trim root `index.html` to link into `/vault/` instead of listing
  individual articles.

## Error handling

- Manifest fetch failure (e.g. offline, 404) → sidebar shows a simple
  "couldn't load vault index" message; local drop-zone mode still works
  since it doesn't depend on the manifest.
- A file that fails to parse (corrupt docx/pptx, unsupported format dropped
  in local mode) → main pane shows an inline error state naming the file,
  rather than a blank screen or thrown exception.
- Unsupported file type dropped in local mode → explicit "unsupported file
  type" message listing accepted extensions.

## Testing approach

- Unit-level: the pptx parser (title/body/bullet extraction, media
  resolution) is the highest-risk piece and should get direct tests against
  a couple of real sample `.pptx` files (a title slide, a bulleted content
  slide, a slide with an image).
- Manual/browser verification for the other renderers (md/docx/txt) given
  they lean on well-established libraries (`marked`, `mammoth.js`) — focus
  testing on the Forage-restyling layer on top of their output.
- Manual verification of: manifest generation on push, sidebar navigation,
  sidenote persistence across reloads, split-pane behavior, local drag-drop
  mode with no vault/network dependency, light/dark theme parity.

## Open questions / risks

- PPTX parsing is bespoke and is the largest source of fidelity risk —
  complex slide masters, SmartArt, or charts (not plain text/images) will
  likely render incompletely. Scoped intentionally to text + inline images
  only, per user decision.
- Mammoth.js docx image extraction embeds images as base64 data URIs, which
  can bloat page weight for image-heavy docs; acceptable for now, worth
  revisiting if it becomes a real problem.
